Commands:

Limits: MCP supports newline JSON-RPC over stdio, not HTTP MCP or A2A. Existing socket paths are not replaced automatically; an operator must resolve stale endpoints. Session tool calls enforce scope in core; possession of operator credentials intentionally grants operator authority. Socket/state credentials protect against other OS users, not processes already running as the same OS user. Discovery is read-only and does not adopt sessions. Flags precede positional METHOD/JSON arguments. `init` enrollment is not transactional with the manifest write: once `enrollAgent` returns, a session has been minted or adopted and a connection file exists, and any later failure strands it with no manifest and no report naming it — a target that is readable and traversable but not writable reaches that state through `MkdirAll`; the two ways to close it are recorded at the call site in `cmd/agent-commons/init.go`. The adopted-versus-created label these commands report degrades to `unknown` when the pre-RPC `sessions.list` snapshot fails, and that downgrade is untested because the snapshot and the enroll RPC share one socket and one operator token; a stdlib-only route to a test, needing no production injection point, is recorded at `enrollAgent` in `cmd/agent-commons/enrollment.go`. The service `init` starts leaves a residual it never reclaims: the private stderr capture created in the state directory is unlinked on every path out, but the started service keeps writing `internal/transport`'s one line per authenticated RPC into the nameless inode for its lifetime — roughly 64 bytes per call, about 61 MiB per million, invisible to `ls` and `du`, reclaimed only when the process exits. It carries actor and method, no parameters and no credentials, so it is a space limit rather than a disclosure one; restarting the service is the only way to reclaim it, and it is written for operators in SERVICE.md. The unlinked inode is `init`'s alone, but the log volume is not: `internal/supervision`'s launchd plist and systemd unit name no stderr destination and no `service` flag sets one, so a supervised service writes the same line per RPC to journald or the system log for its lifetime, under the supervisor's retention rather than any this tool chose. Flag-parse errors reaching a person once is a property of every command routing its parse through `parseFlags` rather than anything the process boundary can enforce: `flag.ContinueOnError` writes the message and the usage listing itself, `parseFlags` marks what comes back as already reported, and a new FlagSet that calls `fs.Parse` directly reintroduces the double print. Nothing in the compiler or `go vet` catches that; the guard is the built-binary test in `integration/flag_error_report_test.go`, which has to gain a row for each new FlagSet.
